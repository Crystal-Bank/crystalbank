# crystal-es upgrade: 0.6.6 → 0.9.0 (Reactor pattern, reduced Command scope)

This document records why and how the app's event-sourcing library, [crystal-es](https://github.com/tristanholl/crystal-es), was upgraded from the previously vendored `~> 0.6.6` to `~> 0.9.0`, and the architectural shift that upgrade required across every domain.

## Findings: what changed upstream

`crystal-es` moved through several breaking changes between 0.6.6 and 0.9.0:

| Version | What changed |
|---|---|
| 0.7.0 | Preparatory work; no app-visible API change. |
| 0.8.0 (commit `8d903219`, "Reorganize command handler and introduction of reactors") | **The breaking change this migration is about.** `ES::Command` shrank from a class carrying `@event_store`/`@event_handlers` and an overridable `call` method, to a pure data `struct` — just `aggregate_id` plus whatever typed payload the app adds. All the behavior that used to live in `Command#call` moved to a new `ES::CommandHandler(C)`, which hydrates the aggregate, enforces invariants, and appends events. A new `ES::Reactor` became the *only* thing allowed to subscribe to the `EventBus` from application code — it consumes one event and calls a `CommandHandler` directly; it has no business logic of its own. `EventBus#subscribe` also gained a safety check: it now raises `ES::Exception::InvalidState` at subscribe time if the handler (`Reactor` or `Projection`) declares no matching `call`/`apply` for the event being wired to it. |
| 0.9.0 | Adds **opt-in** payload encryption / crypto-shredding (`define_event(..., encrypted: true)`, `ES::Config.encryption`, key stores). Verified via source diff that this is fully opt-in: with `ES::Config.encryption` left unconfigured and no event declaring `encrypted: true`, every code path (`encode_body`, `decode`, event constructors) behaves identically to the pre-encryption library. This app does **not** adopt encryption — see Guardrails below. |

## Plan: the conversion pattern

The reactor pattern replaces the old `Command`-subclass-as-both-data-and-behavior with a three-part split. Reference implementation: `app/src/domains/account_management/accounts/commands/opening/` and `.../reactors/opening/`.

**Before** (0.6.6): one `ES::Command` subclass did everything.
```crystal
class ProcessApproval < ES::Command
  def call
    approval = Approvals::Aggregate.new(@aggregate_id.as(UUID))
    approval.hydrate
    return unless approval.state.source_aggregate_type == "Account"
    # ...hydrate the target aggregate, build the event, @event_store.append(event)...
  end
end
```

**After** (0.9.0): a `Reactor` (routing only) hands off to a `Command` struct + `CommandHandler` (business logic):
```crystal
# reactors/opening/on_approval_completed.cr
class OnApprovalCompleted < ES::Reactor
  def call(event : Approvals::Collection::Events::Completed)
    approval = Approvals::Aggregate.new(event.header.aggregate_id, event_store: @event_store, event_handlers: @event_handlers)
    approval.hydrate
    return unless approval.state.source_aggregate_type == "Account"

    Accounts::Opening::Commands::AcceptHandler.new(event_store: @event_store, event_handlers: @event_handlers).handle(
      Accounts::Opening::Commands::Accept.new(aggregate_id: approval.state.source_aggregate_id.as(UUID))
    )
  end
end

# commands/opening/accept.cr
struct Accept < ES::Command
end

class AcceptHandler < ES::CommandHandler(Accept)
  def handle(command : Accept)
    account = Accounts::Aggregate.new(command.aggregate_id, event_store: @event_store, event_handlers: @event_handlers)
    account.hydrate
    @event_store.append(Accepted.new(actor_id: nil, aggregate_id: command.aggregate_id,
      aggregate_version: account.state.next_version, command_handler: self.class.to_s))
  end
end
```

The same split applies to the directly-API-invoked "Request" commands (previously `class Request < ES::Command; def call(r, c); ...; end; end`), which also became a `struct Request < ES::Command` (payload fields, `aggregate_id` generated by the controller via `UUID.v7`) + `class RequestHandler < ES::CommandHandler(Request)`.

Applied across every domain with a command triad: `account_management/accounts` (opening, closure, blocking/unblocking), `account_management/virtual_accounts`, `api_keys` (generation, revocation), `approvals` (creation, collection, rejection), `customers`, `roles` (creation, permissions_update), `scopes` (creation, name_change), `ledger/transactions`, `payments/sepa/credit_transfers`, `users` (onboarding, assign_roles, remove_roles).

Excluded from the conversion: `Platform::Types::Commands::Fetch*` and `Platform::Reset::Commands::Request` (no aggregate to target — read-only or system-wide utilities) and `ApiKeys::Authentication::Commands::Request` (a credential check, not a state change). These became plain classes, no longer `ES::Command` subclasses.

## Guardrails followed

- **No encryption anywhere.** `ES::Config.encryption` is never set; no event declares `encrypted: true`; `.env-dev.template`/`.env-test` were not touched. Verified: `grep -r encrypt app/src` shows only the pre-existing bcrypt hashing of API-key secrets, unrelated to crypto-shredding.
- **Controllers resolve `Context` before constructing a Command.** `CommandHandler#handle(command : C)` only receives the typed struct — `context.scope`/`context.user_id` extraction and the "Invalid scope" guard moved into the API controller, before the struct is built. The one place a command handler still needs the full `Context` (not just individual fields) is `Accounts::Opening::Commands::RequestHandler`, which calls a scope-filtered cross-domain query (`Customers::Queries::Customers#find_all(context:, ...)`) — there the `Context` value object is carried on the struct as a field, since it's itself plain data.
- **The caller picks `aggregate_id` up front.** Every command that creates a new aggregate — a top-level "Request", or a secondary aggregate like an approval request — has the caller generate `UUID.v7` and pass it in explicitly, rather than relying on the event constructor's implicit default. This is why most reactor→handler call sites no longer need a return value the way the old `Approvals::Creation::Commands::Request.new.call(...)` did.
- **`EventBus#subscribe`'s new fail-fast check is a feature, not friction.** It caught a real pre-existing bug during this migration (see below) rather than only validating the new Reactor wiring.

## What the new validation caught

`EventBus#subscribe` now raises `ES::Exception::InvalidState` at boot if a `Reactor` or `Projection` declares no `call`/`apply` matching the event it's subscribed to. This is new in 0.8.0 — the old library had no such check. Rewiring `event_bus.cr` to the new `Reactor` classes hit one genuine, pre-existing gap unrelated to the command/reactor conversion itself: `Events::Projections::Events` (the cross-cutting audit-log projection) was subscribed to 13 event types — `Accounts::Closure::Events::{Requested,Accepted}`, `Roles::PermissionsUpdate::Events::{Requested,Accepted}`, `Scopes::NameChange::Events::{Requested,Accepted}`, `Users::AssignRoles::Events::{Completed,Rejected}`, `Users::RemoveRoles::Events::{Requested,Accepted,Completed}` — that it declared no `apply` overload for. The old library silently tolerated this; the new one refuses to boot until it's fixed. Added the missing `apply` overloads in `app/src/domains/events/projections/events.cr`, following the file's existing two patterns (event body carries `scope_id` directly, or a self-lookup via `scope_id_for` against a prior event on the same aggregate), plus one new pattern for `Roles::PermissionsUpdate::Events::Requested`, whose body has no `scope_id` and which lands on a brand-new secondary aggregate — resolved via `scope_id_for(body.role_id)`, looking up the *role's* prior audit record instead of the update-request aggregate's own (nonexistent) one.
